LESSON 02

第二课：模型切换与参数配置

第一课完成！现在进入第二课：模型切换与参数配置。

这一课的目标不是简单地学会切换模型，而是学会根据任务难度选择合适的 Agent、模型和推理强度，避免浪费订阅额度。

我们需要掌握五个概念：

配置项 作用
Provider 选择 Codex 或 Claude Code
Model 选择具体的大模型
Reasoning Effort 控制模型推理强度
Interaction Mode 控制 Agent 的交互或工作方式
Runtime / Permission 控制文件修改、命令执行等权限

不同 Provider 支持的参数可能不同，并不是所有模型都可以配置上述全部选项。

步骤 2：理解推理强度

Reasoning Effort 是值得重点学习的参数。同一个模型使用不同推理强度，响应时间、额度消耗及解决复杂问题的能力可能不同。

相对推理开销示意

Low — 简单修改、生成注释、格式调整
Medium — 常规开发、源码分析、接口实现
High — 复杂 Bug、并发问题、架构分析
XHigh — 高难度重构、复杂系统设计

相对推理开销示意，并非实际 Token 消耗比例。具体档位取决于模型。

例如，你的盒子 IM 项目可以这样配置：

任务 推荐强度
给 Java 方法添加注释 Low
编写普通 CRUD 接口 Medium
梳理 Kafka 消息发送链路 Medium
分析 Redis 缓存一致性 High
分析消息重复消费 High
设计端到端消息幂等机制 High / XHigh
排查 K8s 多节点消息丢失 High / XHigh

没有必要所有任务都使用 XHigh。 推理强度越高，也不意味着每一个任务的结果都一定更好。

注意，Plan 是交互方式，不等同于操作系统级只读权限。

步骤 4：配置 Agent 权限

根据 T3 Code 官方文档，目前提供以下权限模式，具体选项取决于 Provider。

权限模式 行为 推荐程度
Supervised 修改文件、执行命令时请求审批，部分只读操作可直接进行 初学首选
Auto-accept edits 自动批准文件编辑，其他操作可能需要确认 日常开发
Auto 自动审查常规操作 熟练后使用
Full access 命令和编辑通常不需要审批 谨慎使用

建议现在打开：Settings → General → New threads → Permissions

将新会话默认权限设置为 Supervised。

这样可以避免 Agent 未经确认就修改重要文件、执行危险命令或者影响你的项目环境。

步骤 5：配置默认模型

T3 Code 支持记住模型选择，也支持项目级默认模型。

如果模型列表缺少某个模型，可以进入：Settings → Providers → Models

添加自定义模型。不过，添加模型名称并不代表你的账号获得了该模型的使用权限。

结合你的 Java 后端开发和面试准备需求，我建议采用以下三套配置。

配置 适用 模型参数
A：轻量任务 写文档、改注释、简单代码 Mini / Haiku · Low · Default
B：日常开发 Java 接口、源码分析、业务开发 GPT 主力模型 / Sonnet · Medium · Default
C：复杂任务 分布式系统、并发问题、架构重构 GPT 高能力模型 / Opus · High · Plan

这三套是建议的使用策略，不是 T3 Code 已经内置的三个预设。

LESSON 03

第三课：多 Agent 并行开发与任务编排

前两课已经掌握了项目管理、模型切换和权限配置。现在开始学习 T3 Code 最有价值的功能：让多个 Agent 同时为一个项目工作。

这一课依然使用你的 box-im 项目进行实战。

1. 理解四种多 Agent 协作方式

① 并行执行

用户分配任务
→
Codex：分析消息幂等 / Claude Code：分析缓存一致性
两个 Agent 分别执行独立任务，互不等待。

② 串行协作

Claude：设计方案
→
Codex：实现代码
→
Claude：审查代码
上一个 Agent 的输出作为下一个 Agent 的输入。

③ 竞争与交叉验证

同一个复杂问题
→
Codex 方案 A / Claude 方案 B
→
比较并选择方案
适合复杂 Bug、技术选型、架构设计。

④ 主从式任务编排

主 Agent：拆解任务、汇总结果
→
后端 Agent / 测试 Agent / 审查 Agent
由主 Agent 自动拆解和调度子任务，需要相应的 Agent 或编排工具支持。

注意：多个 Thread 并行运行，不等于自动化多 Agent 编排。 前者由你分配任务，后者则由程序或主 Agent 自动分配任务、传递结果和管理依赖关系。我们需要区分 T3 Code 自身的功能与底层 Agent 的能力。

3. 为什么多个 Agent 能同时运行？

T3 Code 管理层

T3 Code 管理层
→
Thread A · 独立上下文 / Thread B · 独立上下文
→
Codex Runtime / Claude Runtime
→
D:/Project/box-im
共享项目目录（本次只读）

每个 Thread 拥有独立的会话上下文和 Agent 执行状态。T3 Code 负责管理这些会话，而 Codex、Claude Code 各自负责实际的推理与工具调用。

可以类比 Java 中的并发任务：多个任务独立执行，但是可能访问同一份共享资源。

如果两个 Agent 都只是读取源码，通常没有问题；如果它们同时修改同一个文件，就可能产生冲突。

这也是后续学习 Git Worktree 的原因。

**子 Agent A：Claude Code**

- 检查重复提交、Kafka 重试和重复入库问题。

**子 Agent B：Codex**
- 分析群成员缓存一致性。

5. 如何让便宜模型处理简单任务？

这是你之前学习 Magpie 时就想实现的功能。在支持跨模型委派的 T3 Code 版本中，可以尝试通过主 Agent 的提示词实现任务分配策略。

你是主编排 Agent。按照任务复杂度分配工作：简单任务委派给可用的 Mini 或 Haiku 模型；普通任务使用 Sonnet 或 GPT 主力模型；复杂任务使用 Codex High；核心架构任务采用 Codex 与 Claude Opus 交叉验证。先查询 orchestrator_capabilities，再使用 delegate_task。独立任务并行执行，有依赖的任务串行执行。指定模型不可用时向我报告。最终由你核查结果并汇总。未经批准不要修改项目源码。

这是基于提示词的路由策略，并非 T3 Code 内置的确定性路由算法。

6. 多 Agent 使用时的注意事项

场景 推荐做法
多 Agent 阅读源码 使用 Local
多 Agent 同时修改代码 使用独立 Worktree
两个 Agent 修改同一个方法 串行执行
多个 Agent 同时运行 Maven 注意 CPU、内存和测试资源冲突
多个 Agent 连接 MySQL、Redis 隔离测试环境
简单任务 单 Agent 即可
核心架构设计 多 Agent 交叉验证

特别注意，Git Worktree 只能隔离代码工作目录，不能自动隔离数据库、Redis、Kafka 和端口等运行资源。

对于 Java 项目，初期建议同时运行 2～3 个 Agent，不要一开始就启动十几个。多 Agent 并行也会消耗更多模型额度。

LESSON 04

第四课：Git Worktree 工作区隔离与多 Agent 并行修改代码

上一课已经完成了多 Agent 并行执行与任务编排。但是，如果 Codex 和 Claude Code 同时修改一个项目，就可能出现代码覆盖、文件冲突和测试结果不准确等问题。

这一课我们学习如何利用 Git Worktree，让多个 Agent 各自在独立的工作目录中开发，最后将代码合并到主分支。

1. 为什么需要 Git Worktree？

# 多 Agent 自动化软件开发工作流

你是当前 Java 项目的主编排 Agent，负责组织开发、审查、修复和测试。

## 一、执行前检查

调用 orchestrator_capabilities，确认当前可用的 Provider、模型、任务委派能力和工作区隔离能力。

必须使用真实的 T3 Code 编排工具，不允许角色扮演模拟多个 Agent。

## 二、开发阶段

委派 Codex 开发 Agent：
- 分析项目源码。
- 为私聊消息批量入库幂等机制补充单元测试。
- 使用独立 Worktree。
- 运行相关测试。
- 提交本地 Git Commit。
- 返回工作区路径、分支、Commit SHA 和测试结果。

## 三、独立审查阶段

开发完成后，委派 Claude Code 审查 Agent：
- 确认审查的是开发 Agent 最新提交。
- 审查相对于基础提交的完整 Diff。
- 检查业务正确性、并发安全、幂等性、异常处理和测试质量。
- 输出 P0/P1/P2/P3 分级问题。
- 禁止直接修改开发代码。
- 输出 PASS 或 REQUEST_CHANGES。

## 四、自动修复阶段

如果审查发现 P0 或 P1：
- 将审查报告交回开发 Agent。
- 要求逐项核查并修复。
- 重新运行测试并提交新版本。
- 创建新的 Claude Code 审查任务，审查最新 Commit。

最多进行两轮修复与重新审查。

如果仍有未解决的严重问题，停止并向我报告。

## 五、测试阶段

审查通过后，委派可用的低成本模型：
- 验证实际测试命令与退出状态。
- 检查关键测试覆盖情况。
- 在隔离测试环境中运行必要测试。
- 禁止连接生产数据库或修改生产配置。

## 六、最终验收

主 Agent 输出：
- 每个子 Agent 的真实任务标识
- 完整任务执行记录
- 修改文件列表
- Git 分支和最终 Commit SHA
- 审查问题及修复结果

3. 实操二：通过 Tailscale 建立私有网络

下面是我针对你的盒子 IM 项目设计的规则模板。

# AGENTS.md

## 项目说明

本项目是基于 Java、Spring Boot、Netty、MySQL、Redis、Kafka 和 Kubernetes 的分布式即时通信系统。

## 开发规范

- 修改代码前先阅读现有实现。
- 优先复用已有组件，不重复造轮子。
- 遵循当前项目的模块划分与代码风格。
- 不进行与当前任务无关的重构。
- 分析结论必须提供源码路径和方法名称。

## 分布式系统规范

涉及消息发送时，必须考虑：

- 消息幂等性
- 消息顺序性
- Kafka 重复消费
- Redis 与 MySQL 数据一致性
- WebSocket ACK 与离线补拉
- 多节点并发与故障恢复

涉及缓存时，必须考虑：

- 缓存穿透、击穿与雪崩
- 并发读写
- 缓存失效时机
- 多实例环境下的一致性

## 测试规范

- 修改业务逻辑后运行相关 Maven 测试。
- 优先使用隔离测试环境。
- 禁止连接生产数据库。
- 不得虚构测试结果。
- 测试失败时报告具体原因。

## Git 规范

- 多 Agent 修改代码时使用独立 Worktree。
- 不覆盖其他 Agent 的未提交修改。
- 未经用户批准不得 Push、Merge 或部署。
- 禁止擅自执行 git reset --hard。

## 任务交付规范

任务完成后必须说明：

1. 修改文件列表。
2. 实现思路。

第三步：编写第一个原生工作流

不要一开始就编写复杂的多 Agent 流水线。我们先练习一个包含人工审批节点的简单工作流。

参考官方 Workflow API，编写（保留原课代码，未在本机验证）：

const { workflow, step, ask, stop, title } = T3;

export default workflow(
  "java-review",
  {
    version: 1,
    payload: Schema.Struct({
      task: Schema.String
    })
  },

  Effect.fn(function* (payload) {

    yield* title(`Java Review: ${payload.task}`);

    const summary = yield* step(
      "prepare",
      { returns: Schema.String },
      Effect.succeed(payload.task)
    );

    const answer = yield* ask("approve", {
      title: `是否批准任务：${summary}`,
      choices: ["Approve", "Reject"]
    });

    if (
      Option.isNone(answer) ||
      answer.value.choice !== "Approve"
    ) {
      return yield* stop("用户未批准");
    }

    return {
      approved: true,
      task: payload.task
    };
  })
);

这是基于官方示例改写的最小工作流，用来验证输入参数、步骤执行和人工审批，不会实际修改 Java 代码。
