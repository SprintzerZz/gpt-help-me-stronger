02 · TWO-PHASE COMMIT

为什么需要两阶段提交？

重点看事务提交时的三个检查点，它们不是 UPDATE 执行时的全部日志动作。

执行 UPDATE
产生 Undo / Redo
① Redo Prepare
准备提交
② Binlog 提交
写入完整事务
③ Redo Commit
完成事务
如果先只提交一种日志就直接返回成功，宕机时可能出现「InnoDB 数据与 Binlog 记录不一致」。内部两阶段提交负责协调二者，恢复时可以识别处于 Prepare 状态的事务。

03 · CRASH RECOVERY

假设 MySQL 突然宕机？

选择一个崩溃时间点，点击按钮查看恢复结果。

💥 场景 A：Prepare 前

事务正在执行，尚未完成两阶段提交协调。

结果：回滚未提交事务。
恢复时不会把它当作已提交事务；未提交的改动需要撤销。

💥 场景 B：Prepare 后、Binlog 提交前

Redo 已是 Prepare，但未发现完整提交的 Binlog 事务。

结果：回滚。
对于未提交到 Binlog 的 prepared 事务，恢复阶段不应把它当作成功提交。

💥 场景 C：Binlog 提交后、Redo Commit 前

Redo 处于 Prepare，Binlog 已有完整可恢复的事务记录。

结果：提交。
恢复流程可以根据已完成的 Binlog 事务判定 prepared 事务应提交，并利用 redo 恢复相关页更改。

实际可靠性与 sync_binlog、innodb_flush_log_at_trx_commit、存储设备及故障类型有关。这里是典型崩溃恢复逻辑的教学模型。

04 · LOG COMPARISON

Undo Log

记录怎样撤销这次修改，用于事务回滚与 MVCC 旧版本读取。更新时产生 undo 记录，写入 undo 页的修改也会受到 redo 保护。

记录物理页相关的更改，支撑崩溃恢复与 WAL。数据页不必在每次事务提交时立即刷盘。

05 · INTERVIEW NOTES

面试 40 秒怎么回答？

执行一条 UPDATE，MySQL 首先经过连接器、解析器和优化器，由执行器调用 InnoDB。引擎按照索引定位记录，必要时将数据页从磁盘加载到 Buffer Pool，并获取相应的行锁。修改前生成 Undo Log，用于回滚和 MVCC；随后修改内存中的数据页，将其标记为脏页，同时产生 Redo Log。

事务提交时，为了让 InnoDB 的 Redo Log 和 Server 层的 Binlog 保持一致，会进行内部两阶段提交：Redo Prepare → Binlog 提交 → Redo Commit。成功提交后释放事务持有的行锁并返回结果。脏页可以由后台异步刷盘，不要求每次提交立刻写回数据文件。
06 · FOLLOW-UP QUESTIONS

面试官继续追问

Q1：为什么更新了数据，却不立即刷盘？

因为 InnoDB 使用 WAL（Write-Ahead Logging）。事务相关 redo 按持久化策略处理后，脏数据页可延迟刷盘，从而避免每次事务都随机写入数据页。注意：redo 写入内存、写到操作系统缓存和 fsync 到持久存储是不同概念。

Q2：Buffer Pool 是不是 B+ 树？

不是。B+ 树是索引组织结构；Buffer Pool 是内存缓冲池，存放从表空间读取的数据页 / 索引页等。定位记录时遍历 B+ 树涉及的页，如果缓存未命中，才从磁盘加载相应页。

Q3：是不是先写 Redo Prepare，再修改 Buffer Pool？

不是。Redo 是在事务执行过程中随着页面修改产生的；Prepare 指事务提交协调中的一个阶段。不能把“产生 redo”“把 redo 写入日志缓冲”“写入 redo 文件”“Prepare 状态”混为一谈。

Q4：行锁什么时候释放？

在典型事务性 UPDATE 中，InnoDB 持有必要的记录锁直到事务结束（COMMIT 或 ROLLBACK）。不是一修改完 Buffer Pool 就立即释放。实际锁范围与访问路径、隔离级别等有关。

Q5：为什么 Binlog 和 Redo Log 不能合并？

Redo 是 InnoDB 内部用于页级崩溃恢复的日志；Binlog 是 Server 层的变更事件日志，面向复制、归档和时间点恢复。两者粒度、使用范围与生命周期不同。
