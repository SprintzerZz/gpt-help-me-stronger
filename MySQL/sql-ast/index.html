SQL 的语法树解析（AST）

一条 SQL 如何从文本变成结构化表示？通过三个阶段、教学示例和可点击语法树理解解析过程。

① SQL 解析全过程

点击下面的阶段卡片，查看该步骤如何处理同一条 SQL。

阶段 1 / 3
示例 SQL
SELECT id, name FROM users WHERE age > 18;
STEP 1 词法分析：拆成单词

数据库的词法分析器按规则扫描 SQL，输出带类型的 Token。

输出：Token 序列。此处仅展示关键 Token；空白和注释未逐一呈现，实际解析细节取决于数据库实现。
STEP 2 语法分析：组装 AST

语法分析器根据 SQL 语法规则形成树。点击树中的 SELECT / COLUMNS / FROM / WHERE 节点查看含义。

结构化文本
SELECT ├── COLUMNS │ ├── id │ └── name ├── FROM │ └── users └── WHERE └── age > 18
SELECT：查询语句的根节点，下面包含投影列、数据来源和过滤条件。

这是教学用简化 AST，不代表 MySQL 内部实际节点类型和完整树结构。

STEP 3 语义分析：能否正确解释

语法正确，不代表语句能被正确执行。数据库还要进行名称解析、类型处理和权限检查等工作（实际内部处理顺序因数据库版本而异）。

✓ 表检查
users 是否存在？
✓ 列检查
id、name、age 是否存在？
✓ 类型处理
age > 18 的类型是否可比较？
✓ 权限检查
当前账号是否有相应访问权限？
典型错误：
SELECT id, name FROM users WHERE no_such_col > 18;
如果列不存在，MySQL 可能报：ERROR 1054 (42S22): Unknown column 'no_such_col' in 'where clause'。

注意：age > 'eighteen' 不一定直接报“INT 与 STRING 不匹配”；MySQL 有隐式类型转换，实际行为取决于上下文和 SQL 模式。

② 为什么 AST 与 SQL 注入有关？

AST 本身不会自动防注入；关键在于参数化查询将 SQL 结构与输入值分开处理。

✕ 危险：拼接 SQL 字符串

"SELECT * FROM users WHERE name = '" + input + "'"

如果把用户输入直接拼进 SQL 文本，可能把输入解释成新的 SQL 语法。

✓ 推荐：参数化查询

SELECT * FROM users WHERE name = ?;

用户输入作为绑定参数中的数据处理，不能把它变成新的 WHERE、OR 或注释结构。

拼接后 SQL（文本发生改变）
参数化 SQL（结构不变）
这只是 SQL 字符串层面的教学模拟，不会连接数据库或执行查询。真实代码请使用 JDBC PreparedStatement、MyBatis #{} 等安全参数绑定；不要用 ${} 拼接不可信输入。

③ 面试怎么回答？

“SQL 解析一般可以从三个阶段理解：先做词法分析，将 SQL 字符串拆成 Token；再做语法分析，校验语法并形成抽象语法树 AST；然后做语义相关检查，例如表和字段是否存在、类型是否合理、权限是否满足。之后优化器会根据查询结构和统计信息选择执行计划。AST 并不是防 SQL 注入的直接手段，防注入的关键是使用预处理语句和绑定参数，把输入当作数据，而不是拼接进 SQL 语法。”

④ 三道面试快问快答

Q1：词法分析和语法分析的区别是什么？
词法分析是“拆词”；语法分析是“按语法规则把词组成树”。
Q2：AST 生成后，SQL 就能直接执行了吗？
不能。后续还需要名称解析、权限及类型检查、优化和执行计划生成等流程。不同数据库内部阶段可能交织。
Q3：为什么 PreparedStatement 有助于防止 SQL 注入？
因为 SQL 的结构和参数值分开处理，绑定的值不会被当成 SQL 关键字或操作符重新解析；但表名、排序字段等动态 SQL 结构仍要使用白名单。
💡 记忆口诀：先拆词，再成树；检查语义，优化执行。
