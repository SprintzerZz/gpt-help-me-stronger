步骤说明

⚡ 三条并行路径

HTTP 主路径：校验 → Redis 暂存 → 路由 →（若有在线目标）Kafka Broker ACK → HTTP 返回
发送结果回程：Channel 写结果 → Kafka 发送结果 Topic → im-platform → Redis ZSet 登记等待
客户端 ACK 回程：cmd=7 → Kafka ACK Topic → im-platform → 更新 DELIVERED
独立后台：Redis 待写列表 → 批量 INSERT MySQL → 清理暂存
这些路径不是严格串行。ACK 等待登记与客户端 ACK 回程可并发；后台落库也可能先于实时送达。

📌 代码细节与边界

`MQPublisher.send()` 等待 KafkaTemplate 返回的 Broker 确认（默认客户端超时配置 5000ms），不等待 im-server 消费，也不等待客户端 ACK。
`DeliveryAckProcessor` 使用 `sendAsync()`，只负责提交异步发布并记录日志；Kafka 失败会记录错误，但此调用没有同步等待 ACK Topic 写入。
后台 `@Scheduled(fixedDelay=100)` 是“上次执行结束后再延迟约 100ms”，不是严格每 100ms 必定落库；每批最多 500 条。
业务语义：HTTP 成功 ≠ 客户端已收到 ≠ MySQL 已落库；HTTP 失败或超时也不一定表示消息未发送，Redis 暂存与部分 Kafka 投递可能已经完成。客户端需要幂等重试与状态核对。

面试一口气讲清楚

“私聊发送时，HTTP 先完成权限校验，再通过 Redis Lua 原子分配消息 ID 和会话 seqNo，并把待入库消息暂存 Redis。服务端批量查询接收者各终端和发送者其他终端的在线节点，将接收者在线终端按 serverId 分组，发送者其他终端另行同步；没有任何在线目标则不发送节点消息。存在节点投递时，同步发布等待 Kafka Broker 确认后返回 HTTP，不等待用户收消息。im-server 推送后通过发送结果 Topic 通知业务侧登记 ACK 等待，客户端另通过 cmd=7 → Kafka ACK Topic 回报送达，两条回程可并发。后台独立批量写 MySQL；离线与超时走补偿。”
