    ④ 四条并行路径与核心口述骨架（继承并深化 V5）

    1) HTTP 主路径（同步）：
   校验/限流/好友/黑名单 → Redis Lua 原子分配 id+seqNo+暂存
   → 1 次 MGET 路由 → (有在线目标) Kafka Broker ACK → HTTP 返回 VO
   （HTTP 成功 ≠ 已落 MySQL ≠ 李四已收到）

2) 发送结果回程（异步，独立于路径 3）：
   ChannelFuture CAS 聚合 → im.result.private.<app> → PrivateMessageListener
   → SUCCESS 登记 Redis ZSet 超时等待 (15s, maxRetries=2)
   → NOT_ONLINE/NOT_FIND_CHANNEL(APP) 触发 OfflinePushService

3) 客户端 ACK 回程（异步，可早于路径 2 到达）：
   李四端 50条/200ms 攒批 cmd=7 → DeliveryAckProcessor(限200条, sendAsync)
   → im.message.delivery_ack → DeliveryAckTask → markDeliveredByReceiver
   → 锁内改暂存 + 锁外批量 UPDATE WHERE status=PENDING AND (id,recv_id) IN (...)

4) 独立后台批写与已读刷库（异步）：
   BatchStore.flush (100ms, 500条/批, 1s预算) 叠加 Redis 已读水位 → INSERT ON DUPLICATE → ACK Lua
   ReadPositionStore.flushPrivateReadPositions (200ms) 检查 minPendingId 延后 → UPDATE → ACK_PRIVATE_DIRTY Lua

    面试 60 秒一口气口述版

    “私聊发消息时，HTTP 先过格式校验、Redis 滑动窗口限流、好友缓存与黑名单校验，随后在单段 Redis Lua 内原子生成全局 ID、会话 seqNo 并暂存到待写 Hash/ZSet，避免会话锁和单条落库写放大；接着一次 MGET 查出接收方多端和自己其他端路由，按 serverId 投递节点单分区 Kafka Topic，拿到 Broker ACK 就返回 HTTP，不阻塞等落库或客户端收包。下游有三条独立异步路径并行：im-server 写出后通过发送结果 Topic 在 ZSet 登记 15 秒超时跟踪（最多补推 2 次，耗尽对 App 走离线 Push 兜底）；客户端攒批上报 cmd=7 回执经批量聚合、锁内改暂存加锁外批量 UPDATE 标记 DELIVERED；后台定时每批 500 条无锁批写入 MySQL 并在写前叠加已读水位线防状态回退。”

    诚实说明当前边界（加分点）
    ① 暂存未刷盘窗口内 Redis 丢内存会丢数据；② 发送接口未做 localId 服务端幂等去重；③ DeliveryAckTracker 当前不删已 ACK 的 ZSet 条目且单次扫 200 条/2s（高 QPS 需清理或扩容扫描）；④ PrivateMessageServiceImpl.initSeqNo 仍用 redisTemplate 且保留了历史 AopContext.currentProxy()。

    ⑤ 面试高频追问卡片（全部基于真实源码）

    1. markDeliveredByReceiver 把 MySQL UPDATE 放锁外，怎么证明和 flushBatch 并发安全？

    flushBatch 持 IM_LOCK_PRIVATE_MESSAGE_BATCH 覆盖“读暂存 → INSERT MySQL → 删暂存”。ACK 先拿同一把锁改暂存：若 ACK 先拿锁，稍后 flushBatch 直接把 DELIVERED 写进库，锁外 SQL 命中 0 行；若 flushBatch 先拿锁，写库并删暂存后释放锁，ACK 见暂存为空，锁外 SQL 精准将已提交的 PENDING 改为 DELIVERED。

    2. 消息还在暂存区没入库，对方就点了“已读”，会不会被批写覆盖回 PENDING？

    双向保护：① flushBatch 写 MySQL 前批量 multiGet Redis 已读水位线，凡 id <= readPos 且非撤回的消息在落库前直接提升为 READED(3)；② flushPrivateReadPositions 检查待写 ZSet 最小 minPendingId <= newId 时主动延后刷库，防止 UPDATE 跑在 INSERT 前面。

    3. 为什么客户端 ACK 正常收到后不删 ZSet？有什么副作用？

    省掉热路径对 ZSet 的 ZREM 写操作，超时扫描直接以消息状态 status == PENDING 为准，已送达直接跳过。但副作用是：每条消息都要在 ZSet 驻留 15 秒再被 scan() 消费，当前每 2 秒最多扫 200 条（100 条/秒），持续高并发下需在 ACK 路径顺手清理或提升扫描速率。

    4. 私聊为什么不用群聊那套 EncodedSendInfo 预编码？

    私聊通常只推给 1 个接收者的 1~2 个在线终端（PrivateMessageProcessor.java:42-51），扇出度极低，直接写 IMSendInfo 即可；而群聊一包要推几百上千个 Channel，预编码收益巨大。但私聊与群聊共用同一个 @Sharable 共享编码器与静态 ObjectMapper。

    5. 离线拉取如何消除 send_id=? OR recv_id=? 全扫并防止已读降级？

    用 60 天窗缓存映射 id 下界，拆成 (recv_id, id) 与 (send_id, id) 两条倒序 SQL 内存去重归并取前 1 万条 + 遗漏好友补拉最后 1 条；把 PENDING 改 DELIVERED 前先批量查 Redis 已读水位，已在 Redis 已读的不降级且 VO 直接标 READED。

    6. 假死连接触发兜底离线推送，为何 pushPrivate(vo, true) 要传 ignoreOnline=true？

    TCP 半开或 App 后台被杀时，Redis 路由 im:user:server_id 仍有最多 600 秒 TTL，此时 imClient.isOnline(recvId) 仍返回 true。只有传 ignoreOnline=true 绕过在线检查才能下发兜底通知，同时靠 24h 去重 key im:push:dedup:p:{id} + 5s 节流 + request_id 防重复推。
