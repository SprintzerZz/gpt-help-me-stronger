    ④ 面试高频追问卡片（基于当前真实源码）

    1. 群消息发完 HTTP 返回成功，数据落 MySQL 了吗？

    没有。HTTP 返回前仅由 Redis 单段 Lua 完成发号与写入 im:message:group:pending 暂存区，真正落库由后台 @Scheduled(fixedDelay=100) 500 条/批异步写入。MySQL 写后若 ACK 删暂存失败，显式主键 + ON DUPLICATE KEY UPDATE id=id 保证重试幂等；但若 Redis 宕机丢内存则存在丢消息窗口。

    2. 去掉群级锁后，怎么保证同一群内 id 与 seqNo 同序？

    GroupMessageBatchStore.ENQUEUE 在同一段单线程 Lua 脚本里同时 INCR 全局 id 与群内 seqNo，因此两者顺序天然严格一致，无需群级分布式锁；且显式校验 < 2^53 - 1 防止 Lua/JS 双精度浮点丢精度。

    3. Kafka 节点 Topic 单分区就能保证群消息绝对零乱序吗？

    存储序号层（id/seqNo）严格有序；但推送层 MQPublisher 仅保证单 JVM 内按提交顺序入单分区。在多线程并发或多实例 im-platform 下，先拿到 seq=100 的线程若停顿，seq=101 仍可能先进入 Kafka 被推送，客户端需按 seqNo 排序与缺号补拉。

    4. 为什么 PullGroupMessageTask 把 retries 设为 0？

    节点推送队列是单分区，负责整台 im-server 所有群的实时下发。若某条毒丸消息反复退避重试，会队头阻塞整节点推送；配合 BatchListenerFailedException(i) 仅将第 i 条直投 .dlq，前 0..i-1 条正常提交 offset，不丢不堵。

    5. 群已读回执怎么避免大群 500 人同时点开压垮 DB？

    PUT /message/group/readed 只执行 ADVANCE_GROUP Lua 推进 Redis 水位线并合并回执区间 minOld:maxNew，不查 DB；后台 300ms 定时任务原子弹出区间，每群只查 1 次 DB（LIMIT 20）并向发送方汇总推 1 次 RECEIPT；另由 500ms 任务用 GREATEST 批量持久化到 im_group_read_position。

    6. 群已读异步落库源码里藏着什么微竞态？

    ReadPositionStore.flushGroupReadPositions() 先 multiGet 读游标，写完 MySQL 后直接对 im:readed:group:dirty Set 执行 SREM，没有像私聊 ACK_PRIVATE_DIRTY 那样比对版本号。若在读与删之间用户再次推进游标，新水位要等下次已读才会被重新标脏落库。
